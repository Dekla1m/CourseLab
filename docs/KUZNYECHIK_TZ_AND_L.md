## 1. Техническое задание

Разработать прототип аппаратного шифратора «Кузнечик» на ПЛИС Artix-7 и выбрать способ реализации линейного преобразования L по результатам сравнения быстродействия и аппаратных затрат. ### 1.5. Занятость сообщением и аппаратная смена ключа

Дополнение по решению пользователя от **02.11.2026**.

В Encrypt_TOP реализован выход **busy_all_message**:

- устанавливается при фактическом приёме первого блока: data_input_valid && data_input_ready;
- остаётся единицей во время обработки всех блоков сообщения и в паузах между ними;
- снимается при выдаче последнего результата: data_output_valid=1 и data_output_last=1;
- очищается синхронным сбросом, который отменяет текущую операцию;
- не блокирует приём промежуточных блоков: data_input_ready определяется занятостью отдельным блоком, а не busy_all_message.

Завершение здесь означает выдачу последнего результата **из Encrypt_TOP**, а не окончание передачи UART. По текущему решению пользователя после этого уже разрешена смена ключа. Снятие busy_all_message не является признаком завершения ответа ПК.

**Аппаратная загрузка активного ключа.** `kuz_key_schedule` рассчитывает K1…K10 на 100 МГц. `kuz_TOP` управляет допуском загрузки и хранит активный набор на 200 МГц. Системный адаптер ввода и банк вместе должны:

1. Фиксировать новый корректный ключ только при busy_all_message=0; при busy_all_message=1 активный ключ сохраняется без изменений, включая паузы между блоками.
2. Атомарно обновлять все 256 бит ключа и подавать один и тот же active_key всем блокам текущего сообщения. Ошибочный ввод не заменяет активный ключ.
3. Явно подтверждать принятие ключа. При запрете загрузки кандидат должен ожидать подтверждения либо отклоняться с определённым статусом, без изменения active_key; конкретный интерфейс согласовать при реализации.
4. Не допускать обработку данных до первоначальной успешной загрузки ключа.
5. Исключить одновременные запись нового ключа и приём первого блока на одном фронте. Одного зарегистрированного busy_all_message для этого недостаточно: до фронта приёма он ещё равен нулю. Приоритет отдать приёму блока с текущим ключом, а загрузку нового ключа отложить; событие data_input_valid && data_input_ready учесть в разрешении записи.

Приёмка блока ключа: проверить загрузку до сообщения, попытки смены во время вычисления и между промежуточными блоками, запрос одновременно с началом сообщения, разрешённую загрузку после последнего результата и сброс. Ни один блок сообщения не должен случайно получить другой ключ. При отмене сообщения сбросом возможное повторное использование ключа определить контрактом блока ключа.

Аппаратный блок смены ключа остаётся отдельной задачей. Запрос смены режима ENC/DEC поступает от кнопки. Условия применения режима согласуются с очередями и состоянием ответа. [Управление режимами](SYSTEM_BUS_AND_PROGRAMMER.md#кнопки-и-границы-переключения)

## 2. Как работает «Кузнечик»

### 2.1. Общая структура

«Кузнечик» обрабатывает блок из 16 байт. Из 32-байтового исходного ключа получают десять 16-байтовых раундовых ключей. Шифрование состоит из девяти последовательностей X → S → L и заключительного XOR с десятым ключом. Определения и контрольные значения приведены в [ГОСТ Р 34.12-2015](https://tc26.ru/standard/gost/GOST_R_3412-2015.pdf) и [RFC 7801, разделы 4–5](https://www.rfc-editor.org/rfc/rfc7801.html#section-4).

```text
Входной блок
 → XOR K1 → S → L
 → XOR K2 → S → L
 → …
 → XOR K9 → S → L
 → XOR K10
 → Шифротекст
```

X складывает блок и раундовый ключ побитовым XOR. S независимо заменяет каждый байт по фиксированной перестановке π из 256 значений, сохраняя его позицию. L смешивает байты посредством шестнадцати шагов R. Эти три операции используются также при выработке ключей.

### 2.2. Представление байтов и арифметика

Используется запись:

```text
Блок:     a15 a14 … a1 a0
Verilog:  a[127:120] = a15; a[7:0] = a0
Python:   T[0] = a15; T[15] = a0
```

В длинной hex-строке каждые две цифры обозначают байт. Разворачивать байты или полубайты для контрольных примеров ниже не нужно.

Байт `b7…b0` соответствует многочлену `b7*x^7 + … + b1*x + b0`. Сложение многочленов — XOR, умножение — полиномиальное умножение с приведением по модулю:

```text
p(x) = x^8 + x^7 + x^6 + x + 1
Полное битовое представление p: 0x1C3
Маска редукции после 8-битного сдвига: 0xC3
```

Это не обычное умножение целых чисел по модулю 256. Например, `80 × 02 = C3` в hex: член x^8 заменяется на x^7 + x^6 + x + 1.

Для генерации констант удобно умножение на x, называемое `xtime`:

```python
def xtime(a):
    return ((a << 1) & 0xFF) ^ (0xC3 if a & 0x80 else 0)
```

Условие проверяет старший бит исходного байта. При цепочке `xtime` редукция выполняется на каждом шаге. В заранее вычисленных XOR-вкладах она уже учтена.

### 2.3. Преобразования R и L

Коэффициенты R для порядка `a15,…,a0` записаны **десятичными числами**:

```text
148, 32, 133, 16, 194, 192, 1, 251,
1, 192, 194, 16, 133, 32, 148, 1
```

Новый байт вычисляется как XOR шестнадцати произведений в поле:

```text
r = 148·a15 XOR 32·a14 XOR 133·a13 XOR 16·a12
    XOR 194·a11 XOR 192·a10 XOR a9 XOR 251·a8
    XOR a7 XOR 192·a6 XOR 194·a5 XOR 16·a4
    XOR 133·a3 XOR 32·a2 XOR 148·a1 XOR a0

R([a15,…,a0]) = [r,a15,a14,…,a1]
L(a) = R(R(…R(a)…)) — всего 16 применений R
```

На каждом шаге коэффициенты закреплены за позициями, а значения байтов меняются. Сдвиг и новый r вычисляются из предыдущего состояния.

### 2.4. Выработка раундовых ключей

Исходный ключ разделяется на две 128-битные половины — K1 и K2. Затем независимо вычисляются 32 константы:

```text
Ci = L(Vec128(i)), i = 1…32
```

`Vec128(i)` — число i в 16 байтах с нулями слева. Каждую Ci получают из её номера, а не из предыдущей константы.

Начиная с `(A,B)=(K1,K2)`, выполняют 32 шага:

```text
(A,B) ← (L(S(A XOR Ci)) XOR B, A)
```

Обе выходные половины используют старые A и B. После шагов 8, 16, 24 и 32 сохраняют очередные пары K3/K4, K5/K6, K7/K8 и K9/K10. Здесь сеть Фейстеля применяется к выработке ключей; шифрование блока выполняет последовательности X, S, L.

### 2.5. Контрольный пример

```text
Исходный ключ:
8899aabbccddeeff0011223344556677fedcba98765432100123456789abcdef

Открытый блок:
1122334455667700ffeeddccbbaa9988

После первого X:
99bb99ff99bb99ffffffffffffffffff
После первого S:
e87de8b6e87de8b6b6b6b6b6b6b6b6b6
После первого L:
e297b686e355b0a1cf4a2f9249140830

Итог после девяти полных раундов и XOR с K10:
7f679d90bebc24305a468d42b9d4edcd
```

Это значения из [контрольного шифрования RFC 7801, раздел 5.5](https://www.rfc-editor.org/rfc/rfc7801.html#section-5.5). В ранних объяснениях исходного чата были исправленные позднее ошибки в порядке половин ключевого шага и значении C1; в этом документе используется итоговая согласованная запись.

## 3. Способ 1: примитивный элемент и таблицы LOG/EXP

### 3.1. Идея

Под «примитивными членами» здесь понимаются степени **примитивного элемента** g: ненулевые элементы поля представляются как `g^k`, где k принимает значения 0…254. Для данного полинома можно выбрать `g = 02` hex. При подготовке документа проверено, что его первые 255 степеней дают все 255 ненулевых байтов, после чего значение возвращается к 01.

Заранее строятся две таблицы:

```text
EXP[k] = g^k
LOG[b] = k, если b = g^k и b ≠ 0
```

Для ненулевых a и c:

```text
a·c = EXP[(LOG[a] + LOG[c]) mod 255]
```

Суммирование показателей — обычное целочисленное сложение. Поскольку сумма лежит в диапазоне 0…508, для приведения достаточно одного условного вычитания 255. Для нулевого операнда результат сразу равен нулю: `LOG[0]` математически не определён.

Например, в этом поле `09 = g^53`, `94 = g^45`; поэтому `09·94 = g^98 = BE` (байты hex, показатели десятичные).

### 3.2. Применение к R

Коэффициенты R постоянны, поэтому LOG[c] вычисляют заранее:

```text
байт a → LOG[a] → прибавление постоянного LOG[c]
       → приведение по модулю 255 → EXP → произведение
```

Полученные произведения объединяют XOR, выполняют сдвиг — получается R. Для L этот шаг повторяют 16 раз. Умножение на единицу можно заменить прямым соединением.

### 3.3. Аппаратная организация и такты

LOG и EXP можно разместить в ROM на LUT или BRAM. Полезный объём одного общего набора — 256 байт LOG и 255 байт EXP при восьмибитных записях; ячейка LOG[0] служебная. Этот объём не равен фактическому расходу BRAM.

В R одновременно нужны 13 нетривиальных произведений. Для параллельного чтения таблиц нужны достаточные порты или копии памяти; один набор таблиц с ограниченным числом портов не обслуживает автоматически все эти обращения за такт. Синхронное чтение BRAM добавляет стадии. При последовательном переиспользовании умножителя увеличивается время одного R.

**Число тактов L для LOG/EXP заранее не фиксировано.** Если весь R комбинационный и укладывается в период, повторное использование одного R даёт 16 вычислительных тактов. Если на зависимый шаг R требуется d тактов, последовательный L требует 16·d тактов без учёта дополнительных стадий интерфейса. Конвейер умножителя сам по себе не устраняет зависимость следующего R от предыдущего.

Преимущество — возможность обслуживать произвольные коэффициенты общей арифметикой. Для фиксированных коэффициентов L затраты на таблицы, преобразования и порты могут оказаться лишними; выбор определяется синтезом и трассировкой.

## 4. Способ 2: XOR-вклады постоянных умножителей, один R за такт

### 4.1. Разложение входного байта

Пусть `a = a0 + a1*x + … + a7*x^7`, а c — постоянный коэффициент. По распределительности:

```text
a·c = XOR тех Bi, для которых ai = 1
Bi = (x^i·c) mod p(x), i = 0…7
```

Здесь ai — биты одного байта, а не индексы байтов блока. Восемь Bi вычисляют до работы устройства. Это базисные вклады, а не таблица всех 256 готовых произведений.

Для `c = 148` десятичное, то есть `94` hex:

```text
Бит входа:  0   1   2   3   4   5   6   7
Вклад Bi:  94  EB  15  2A  54  A8  93  E5
```

Например, `05 = 00000101`: установлены биты 0 и 2. Поэтому `05·94 = 94 XOR 15 = 81`, все значения в hex.

Один выходной бит при умножении на 94 получается так:

```text
y[0] = a[1] XOR a[2] XOR a[6] XOR a[7]
```

Это следует из младших битов восьми вкладов: единицы стоят у EB, 15, 93 и E5. Аналогично получают остальные семь выходов. Умножитель задаётся бинарной матрицей 8×8: вклады Bi — её столбцы, XOR-формулы выходов — строки.

### 4.2. Все используемые вклады

Коэффициент слева — десятичный; восемь вкладов справа — hex, от бита 0 до бита 7:

```text
  1: 01 02 04 08 10 20 40 80
 16: 10 20 40 80 C3 45 8A D7
 32: 20 40 80 C3 45 8A D7 6D
133: 85 C9 51 A2 87 CD 59 B2
148: 94 EB 15 2A 54 A8 93 E5
192: C0 43 86 CF 5D BA B7 AD
194: C2 47 8E DF 7D FA 37 6E
251: FB 35 6A D4 6B D6 6F DE
```

### 4.3. Архитектура L за 16 тактов

В аппаратуре создаётся один комбинационный R: постоянные умножители работают параллельно, их результаты складываются XOR, затем байты переставляются. После каждого шага состояние сохраняется в регистре:

```text
Вход → R → регистр состояния → R → … → результат
       1                       2         16
```

Физически блок R один; регистр возвращает его результат на вход. Счётчик завершает обработку после шестнадцатого вычислительного фронта.

В текущем `l_iterative_16cycles.v` первый R вычисляется уже на фронте приёма `start`, следующие 15 — при `busy=1`. Если вход выставлен после фронта N, результат появляется на N+16. От фронта приёма до фронта результата проходит 15 полных периодов; это тот же процесс, посчитанный от другой точки отсчёта. Тестбенч измеряет от выставления входа после N и получает 16 тактов.

На завершающем фронте новый `start` не принимается, так как выполняется ветка `busy`. При непрерывном `start=1` следующие блоки принимаются через 16 фронтов; у источника, ожидающего `done` перед новой выдачей, могут появляться дополнительные паузы. Интервал блоков нужно измерять по выбранному протоколу.

Константные вклады при синтезе могут превратиться в связи и XOR на LUT; наличие массива в исходном описании не означает обязательную BRAM. Цикл без регистров описывает комбинационную логику и сам по себе не добавляет такты.

## 5. Способ 3: единая матрица L размером 128×128, один такт

### 5.1. Объединение всех шагов

Постоянные умножители, XOR и перестановки линейны над GF(2). Поэтому один R задаётся матрицей MR размером 128×128, а его шестнадцатикратная композиция — постоянной матрицей:

```text
R(a) = MR·a
L(a) = MR^16·a = ML·a
ML = MR^16
```

Умножение и сложение матриц здесь выполняются над GF(2): AND и XOR. Степень 16 означает композицию преобразований.

Разница с предыдущим способом — масштаб предварительного расчёта: там заранее вычислены восемь вкладов каждого байтового умножителя, здесь — 128 вкладов в результат полного L. Во время работы отдельные R и промежуточные редукции уже не выполняются: они включены в ML.

### 5.2. Построение матрицы

1. Зафиксировать нумерацию: бит 0 — младший бит `a[0]` шины, то есть младший бит байта a0.
2. Для каждого j от 0 до 127 создать блок ej, содержащий одну единицу в бите j.
3. Эталонным способом вычислить L(ej).
4. Поместить L(ej) в столбец j матрицы ML.
5. Собрать строки матрицы как маски зависимостей выходных битов.

Для каждого i:

```text
y[i] = XOR входных a[j], для которых ML[i,j] = 1
```

Схематически на Verilog:

```verilog
assign product[i] = ^(a & ROW_MASK_i);
```

`&` оставляет биты, выбранные постоянной маской, а унарный `^` сворачивает их XOR в один бит. Всего получается 128 таких выражений. Матрица содержит 16 384 бинарных коэффициента; при описании постоянными масками это не означает расход 16 384 триггеров или хранение матрицы в BRAM.

### 5.3. Работа за один такт

Между источником входа и выходным регистром находится комбинационная XOR-схема полного L. Если вход выставлен после фронта N и соблюдены временные требования, на фронте N+1 фиксируются y и признак его готовности.

В `l_matrix_onecycle.v` при `start=1` на каждом фронте записывается новый результат, а `done` повторяет валидность входа с регистрацией. Поэтому при непрерывном потоке `done` может оставаться высоким несколько тактов: каждый такой такт соответствует очередному результату.

Один такт — архитектурная задержка. Допустимый период зависит от глубины XOR, нагрузки, размещения и маршрутов. Если 5 нс не выполняются, потребуются оптимизация либо конвейеризация; последняя изменит задержку в тактах.

### 5.4. Связь с известными реализациями

Прямая матрица полного L описана как Matrix в статье Калистру и соавторов. Их R2L повторяет R 16 раз, задавая постоянные умножители полными таблицами результатов на LUT. Наш вариант 2 задаёт те же байтовые функции через восемь базисных вкладов. Совпадение функции не доказывает совпадения физической схемы после синтеза. [Статья, с. 66–67](https://pdfs.semanticscholar.org/4551/809c134da41bbc65f2524887c5463da08f15.pdf#page=3).

Сам принцип XOR-матрицы не является новым результатом проекта. Практический результат работы — реализация, сопоставимое измерение и обоснованный выбор архитектуры для прототипа.

## 6. Как сравнивать три способа

Для LOG/EXP число тактов зависит от памяти и организации умножителей. Для выбранной архитектуры варианта 2 выполняется один R за такт и весь L за 16 вычислительных тактов. Для варианта 3 всё L вычисляется комбинационно с регистрацией результата за один такт.

Задержку и пропускную способность нужно считать отдельно:

```text
Задержка = число периодов от принятой точки запуска / частота
Пропускная способность = 128·частота / интервал приёма блоков в тактах
```

При одинаковой подтверждённой частоте 200 МГц и принятом запуске от фронта источника задержки 16 и 1 такт соответствуют 80 и 5 нс. При интервале приёма 16 и 1 такт идеальные скорости отдельного L составляют 1,6 и 25,6 Гбит/с. Это условные расчёты для L, без пауз интерфейса; они не являются измеренной скоростью полного шифрования.

Если рабочие частоты различаются, отношение задержек составляет `16·f_matrix/f_iterative`. Для пропускной способности дополнительно учитывается фактический интервал приёма. Конвейер из шестнадцати R тоже может принимать блок каждый такт, но это отдельная архитектура с большей задержкой и иным расходом ресурсов.

Честное сравнение требует одинаковых входных/выходных регистров, clock, целевой микросхемы и настроек Vivado. Нужно отдельно учитывать ресурсы ядра и интерфейсного окружения, проверять setup и hold после трассировки и сохранять отчёты для каждого варианта.
